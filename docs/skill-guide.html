Palette · agent skill

Build a deck by asking for one

Palette ships as an agent skill — two files, eight kilobytes, no build step — that works the same in Claude Code and in CUGA. This is how to try it, how to test it from a clean slate, and what broke along the way.

Try it

Two environment variables and one install command. Then ask for a deck in plain English. 

# once, in the Palette checkout
make install
export PALETTE_HOME=$PWD
export RITS_API_KEY=<key>        # IBM-internal; needs the VPN

Claude Code

make skill-install-claude        # -> ~/.claude/skills/palette

Then, in any session: “Build me a 5-slide deck about RAG.”

CUGA

make skill-install CUGA=<cuga-checkout>

# in the CUGA checkout's .env — loaded at startup, survives a new terminal
PALETTE_HOME=/abs/path/to/project-palette
RITS_API_KEY=<key>

cuga start demo_palette

Either host gives you a plan and a question first — approving it is a second turn — then a rendered .pptx. That gate is deliberate: a plan is cheap to change, a deck costs minutes.

What the skill actually is

Two files. No package, no wheel, nothing generated. A skill is a folder you copy where the host scans — the same shape as Anthropic’s pptx skill.

SKILL.md what the agent is told 216 lines
scripts/deck.py the only thing it runs — stdlib only 441 lines

The YAML frontmatter is load-bearing. Its description is the entire routing decision — the host shows only that when deciding whether to load the skill, so it is written as phrases people actually say, not as a summary of what Palette is.

Why there is a helper script at all

deck.py is a wrapper, but for four reasons, each earned by something breaking:

  • Working directory. palette.py only runs from the checkout, but output must land in the agent’s workspace. Told to hold both roots, an agent conflated them and ran a path that does not exist.
  • Detachment. Slow commands run in their own process and are polled, so a host’s step limit cannot cut them short.
  • Completion. verified is computed by stat-ing the file — the agent relays a fact rather than forming a belief.
  • Error relay. A detached build’s output goes to a log the agent cannot see, so status tails it into the JSON.

The dividing line: SKILL.md holds judgment, deck.py holds facts. Anything the model could get wrong in its own favour lives in code. “Is there a deck?” is checkable, so it is code. “Should I ask before building?” is not, so it is prose.

Testing from a clean slate

Five stages, cheapest first, each proving something the next one assumes. Stop at the first failure — a later stage cannot be read while an earlier one is red. 

P=~/code/project-palette;  C=~/code/cuga-agent;  S=~/code/cuga-skills

  1. The repos agree with themselves ~10s · no network, no key

    (cd $P && .venv/bin/python -m pytest tests/ -q)
(cd $C && .venv/bin/python -m pytest tests/unit/test_demo_palette_preset.py \
                                     tests/e2e/skills/test_palette_skill_invocation.py -q)
(cd $S && .venv/bin/python -m pytest -q)

110 passed, 1 skipped   ·   26 passed   ·   13 passed

    No models are involved, so a failure here is a real defect and never the weather. These cover the skill naming only flags palette.py actually has (read out of its argparse), the packaging pointing at code that exists, CUGA’s preset settings, and the agent reaching load_skill.

  2. The installed copies are the real ones ~1s

    make -C $P skill-install CUGA=$C
make -C $P skill-install-claude
make -C $P verify CUGA=$C

12 passed, 1 skipped

    make verify compares every installed copy against skills/palette byte for byte and names the file that differs, then runs the installed deck.py to confirm it resolves $PALETTE_HOME from wherever it was copied to. It takes the locations as input and skips by name for anything you did not give it.

    Do not skip this one. An agent reads its installed copy, never your working tree. Both real CUGA failures were diagnosed at length before anyone noticed the agent was running a copy made before the fix.

  3. Palette builds a deck, no agent involved ~5 min · needs VPN

    cd $P && export PALETTE_HOME=$PWD
S=skills/palette/scripts/deck.py
python $S plan   --request "5 slides on RAG" --out /tmp/p.md --wait
python $S start  --plan /tmp/p.md --out-dir /tmp/deck
python $S status --out-dir /tmp/deck        # until "done": true

    This is the diagnostic pivot. If it passes and stage 4 or 5 fails, the fault is in the agent or the host, never in Palette. --wait is the convenience for a terminal; agents must not use it.

    Or let the test do it: make verify CUGA=$C DECK=1.

  4. Claude Code ~5 min

    make -C $P skill-install-claude

    With both variables in the environment: “Build me a 5-slide deck about RAG.”

  5. CUGA ~10 min

    grep -q '^PALETTE_HOME=' $C/.env || echo "PALETTE_HOME=$P" >> $C/.env
rm -rf /tmp/.venv                # sandbox venv; a stale one once ran deleted code
cd $C && cuga start demo_palette

    Then check from your shell rather than the chat:

    ls -l cuga_workspace/*/deck/deck.pptx
cat  cuga_workspace/*/deck/.palette-build.json    # "state": "done"

Is that deck real?

The one question worth asking, because an agent can describe a file it never wrote. 

D=/tmp/deck
ls -l $D/deck.pptx                                # >100KB, not 4KB
unzip -l $D/deck.pptx | grep -c "slides/slide"    # slide count
unzip -p $D/deck.pptx ppt/slides/slide1.xml | grep -c "IBM Plex"

Palette’s renderer forces IBM Plex, so a deck hand-written with pptxgenjs defaults could not carry it. That grep is the difference between “a deck exists” and “Palette built this deck”.

Four failures worth knowing about

Each one looked like a Palette bug from the chat, and none of them was. All four were the same shape: the work succeeded and the caller never found out.

A sandbox that will not discuss other processes

status → "state": "error", seconds after start

CUGA runs each step under Seatbelt with (allow signal (target self)). So os.kill(pid, 0) against the detached build raises PermissionError, and ps cannot even exec. Both were read as “the process is gone”, so status reported failure on its first poll — minutes before the .pptx could exist. The agent then invented missing dependencies to explain it.

Fix: the build records its own ending in .palette-exit. Reading a workspace file is permitted everywhere; asking about another process is not. Liveness is now tri-state, and “undetermined” never means “dead”.

A step limit that killed a working call

“the palette script timed out while trying to create the plan”

Drafting a plan is one model call: 43–82s locally, ~170s inside the sandbox, against a 120s step. The step was killed; palette.py carried on in its own process and wrote a good 72-line plan seconds later, with nobody looking.

Fix: raising the timeout only moves the cliff. Every slow command now detaches and is polled — plan and edit the same as the build.

A deck that appears before it is finished

"done": true, while three render passes were still running

build-deck renders, lints the geometry, and re-renders to the same path until the layout settles. A complete, valid, correctly-sized .pptx therefore sits on disk for minutes before the build is over. Checking the file before the process handed over a pre-repair deck.

Fix: the build must have ended and the file must be real.

A confirmation gate with no memory

“I keep saying yes but I am still waiting on a deck”

The skill described how to start a deck and never once described a deck that already exists. An agent does not reliably remember earlier turns, so every turn began again at “present the plan and ask the user to confirm”. Saying yes could not break the loop, because the loop was not waiting on the user. The state file proved it: written once when the build started, then untouched for 33 minutes — status was never called again, while a finished five-slide deck sat in the workspace.

Fix: the workflow now opens with step 0 — ask the filesystem where you already are. For that to work, status had to stop erroring on an empty directory and answer none instead. A check that fails when the answer is “nothing yet” is not usable as a check, which is why nothing ever looked.

The thread through all three: a killed step is silent. It tells you nothing about the work while the work finishes anyway. So no command blocks, and completion is a fact on disk rather than a return value.

The lesson that shaped the design

An agent once reported a deck that did not exist. An instruction was added saying not to. It happened again. A stronger one was added. Again.

Prose cannot fix a behaviour the model has a reason to prefer. What worked was moving the claim out of the agent’s judgment entirely: deck.py status stats the file and returns verified. Every instruction failed; one os.stat worked.

Does Palette changing mean the skill changes?

Mostly no. The coupling is eleven strings — three subcommands and eight flags. 

build-plan   --out --context --source
edit-plan    --plan --out
build-deck   --plan --out-dir --json --palette-family

palette.py exposes sixteen flags; the skill touches eight. Change prompts, the pipeline, the renderer, models, post-processing — the skill needs nothing, because it drives the CLI, not the code. Only a renamed command or flag reaches it.

And you do not have to remember. make skill-test reads the argparse and diffs it:

AssertionError: deck.py passes flags palette.py rejects: ['build-deck --out-dir']
FAILED tests/test_skill.py::TestSkillMatchesTheCLI
1 failed, 29 passed in 0.41s

Why this is not a maintenance burden: the skill lives in the Palette repo, next to palette.py. The PR that renames a flag is the PR that updates the skill, and the test fails if it does not. There is no second repo drifting quietly — which is exactly why CUGA’s catalog carries a pointer to Palette rather than a copy.

One copy, owned by Palette

RepoHoldsVerified by
project-palettethe skill itselfmake skill-test
cuga-skillsa catalog entry pointing at Palette, pinned by dirHasha test asserting skills/palette does not exist locally
cuga-agentan installed copy plus environment settingsmake verify CUGA=…

Nothing about the skill is machine-specific — no absolute paths, nothing written at install time. Where Palette lives is per-machine, so it belongs in the environment like $JAVA_HOME. That is what lets the catalog verify the folder by hash, and a test enforces it.

What CUGA has to add

Deliberately little, and none of it explains how to build a deck.

An earlier version carried a supervisor config with a deck-builder persona — load the skill, honour the confirmation gate, poll the build. Every line already lived in SKILL.md, and the copy went stale the moment the skill changed. It was deleted, and a test now fails if it comes back.

What remains is two settings: a step long enough that nothing gets cut short, and auto-continue on, because a deck is minutes of polling and the first progress note written as prose would otherwise end the run mid-build.
